# 实跑验证记录（用桌面控制插件驱动真实程序）

> 目的：无头测试只能证明"代码逻辑自洽"，证明不了"程序在真机上用起来是对的"。
> 这份记录是**启动真实 exe、用 UI Automation 逐步操作、再拿运行产物做判据**的结果。
> 每一轮都留可复核的数字。

## 方法

1. 在 `test-output\ui-live\` 放一套干净运行时（exe + 配置 + SQLite），不预置 `settings.json`。
2. 用 `cmd /c start` 完全分离启动（**不要用会等就绪的启动器：它超时后会终止进程**）。
3. `desktop_windows` → `desktop_snapshot` 读控件树，`desktop_act` 点按/勾选/输入。
4. 判据优先用产物（会话日志、SQLite、审计文件），其次才是界面文字。

### 环境注意事项

- **窗口可能被系统放到屏幕外**（实测出现过 y=1958，屏幕高 1600）。放到屏幕外会让
  UI Automation 枚举变慢甚至超时。用 `desktop_windows -move` 先挪回屏幕内。
- 每读一次控件树约 26–28 秒（这个程序的控件量大）。控件超过约 1500 个之后，
  单次读取会超过 30 秒上限，此时改用 `query` 按名字/类型定位，或改用进程内驱动。
- 沙箱里进程可能无权在 `%TEMP%` 下建目录 ⇒ 测试的 scratch 目录必须建在 `--root` 下。

## 本轮发现并修复

### ① 搜索"找到了"但没滚到（`DashboardForm.FocusCard`）

- 现象：真实程序里搜 `0006H`，卡片仍在窗口外（y=1724，窗口只到 1314），界面毫无反应。
- 两个原因：
  1. 找视口用 `FindControl` 在整棵 `TabControl` 里搜 `AutoScroll` 面板，会命中**别的页面**；
     滚动了也看不见。改为由 `OverviewPageBuilder.Build` 直接返回视口引用。
  2. 定位公式 `card.Parent.Top + card.Top` 漏掉 `section` 在 `stack` 里的偏移，
     越靠后的分组偏得越多。
- 修复：用屏幕坐标换算 —— `PointToClient(card.PointToScreen())` 得到视口内位置，
  加上当前滚动量得到内容坐标，再设 `AutoScrollPosition`（setter 收正值）。
- 回归：新增断言"搜索必须把末尾分组的卡片滚进可视区（y ∈ [0, 视口高)）"。

### ② 随包配置被判为无效（`ControlConfig.Validate`）

- 现象：运行控制页门禁显示 `门禁 mode 只能为 disabled 或 prev…`。
- 原因：0.8.0 把随包 `mode` 改成 `live`，也加了 `WritesEnabled` 接受 live/preview，
  但 `Validate` 的模式白名单没跟着改 ⇒ 配置进 `config_error`。
  写入确实被挡住了（安全），但提示词与随包文件自相矛盾，现场会以为程序坏了。
- 修复：白名单改为 `disabled / live / preview`，并回报实际收到的值。
- 回归：`mode=live` 必须通过校验、`preview` 仍通过、未知 mode 被拒、随包配置能通过校验。

### ③ 测试在受限环境假失败

- 现象：存储套件报 `UnauthorizedAccessException`（无法在 `%TEMP%` 下建目录），
  掩盖真正的缺陷；另外收尾的 `Directory.Delete` 因 SQLite 句柄未及时释放而抛错。
- 修复：scratch 目录改建在 `--root` 下（符合"产物留在仓库内"的约定）；
  收尾删除改为带 GC 的重试且不抛（断言已跑完，清理失败不该决定成败）。

## 一次被我自己的测量方法误导的结论（已用对照实验推翻）

**最初的怀疑**：访问过「数据记录」页之后，进程持续占用约 77% 单核、内存涨到 868 MB。
出现过两次一致的读数，看起来像真的。

**对照实验（决定性）**

| 状态 | 5 秒 / 30 秒内 CPU | 内存 |
|---|---|---|
| 全新启动，未进数据记录页 | +0.02 s（0.4% 单核） | 63 MB |
| 进过数据记录页之后 | +2.3 s（77% 单核） | 868 MB |
| **启动后完全不碰它，静置 30 秒** | **+0.06 s（0.2% 单核）** | **62 MB** |
| 进程内驱动（`--diag-cpu`，切到各页签并让消息泵空跑 5 秒） | 0.00–0.03 s | 0 MB |

**真正的原因**：那 77% 是我自己造成的。这个程序的控件树约 1500 个节点，
**一次 UI Automation 枚举要 26–28 秒**，而我在诊断时反复读树。进程的
`TotalProcessorTime` 把为 UIA 提供者枚举控件的工作全部算了进去。

**结论：不是产品缺陷。** 程序静置 0.2% 单核、62 MB，完全正常。
这条记录保留下来，是因为"测量本身改变被测对象"是这个项目里真实踩到的坑 ——
以后再看到"某页吃 CPU"，先做一次**完全不交互的静置对照**。

**顺带留下的诊断入口** `--diag-cpu`

```
ExperimentMonitorDemo.exe --diag-cpu --tab=3 --capture-first --root=<目录>
```

切到指定页签，让消息泵空跑 5 秒，量 CPU 与内存增量并写 `diag-cpu.json`。
它不依赖 UI Automation，所以不会重犯上面的测量误差。现场怀疑"程序发烫/卡"时可以直接跑它。

## 关于 UIA 自动化测试的成本（供后人参考）

- 单次读整棵树：26–28 秒；控件再多会超过 30 秒上限。
- 因此**只在必要时读树**：优先 `query` 按名字/类型定位，或者干脆用进程内驱动
  （`--diag-cpu` 那种方式）。本次有两次读树超时，都是在这个原因下发生的。
## 第二轮：逐页实跑（诊断 / 趋势 / 记录 / 云端）

### 实跑通过

| 页面 | 判据 | 结果 |
|---|---|---|
| 通信诊断 | `logs/diagnostics.jsonl` 的真实报文 | TX `02 03 08 9A 00 01 A6 76`（站 2、FC03、地址 0x089A=2202、数量 1）→ RX `02 03 02 00 18 FC 4E`（值 0x0018=24），26 ms，`good` |
| 趋势分析 | 页面摘要文本 | `跟随最新 · 模拟 · 1,470 条原始记录 · 可绘制 36 个测点，其余测点无有效工程数值`；按钮 `应用范围 / 回到最新 / 看原始记录 / 导出图片 / 全选 / 清空` |
| 数据记录 | 宽表维度 | `41 轮 × 27 列`；页脚 `本页 41 轮 · 有效轮 41 / 超时轮 0`；耗时 11 ms |
| 云端连接 | 页面文本 | 设备 ID、`— · 确认 0 · 失败 0 · 待发设备 0 · 测点 0`，三段说明文案完整 |

**"可绘制 36 / 37 个测点"是正确的**：少的那个是 `0006H`（位串，无工程数值），界面如实说明了原因，没有把它画成 0。

**连接但未采集时设备分母是 `0/4`**：这是诚实的。诊断页单点读取成功不代表"4 台设备都在采集"，
分母统计的是采集通道的存活，不是连通性。这条语义是对的，不做改动。

### 本轮发现并修复：界面默认列与导出点集不一致

- 现象：数据记录宽表只有 **24 列**（2 + 22 个测点），而导出包含太阳能 3 点。
  也就是说**界面上看不到的测点，导出里却有** —— 用户看不见自己要导出的东西。
- 原因：界面按**分组名白名单**（温度/实验电表/市电）过滤，导出按**分组排除**过滤，
  两套规则各自维护，太阳能正好落在两者的差集里。
- 修复：两边统一用 `PointRole` 判定（`HistoryPage.DefaultColumnVisible` 与
  `ExperimentExport.ExportablePoint` 都只看"是不是测量角色"），分组名只负责显示排序。
- 实测确认：宽表 24 列 → **27 列**，太阳能 3 点可见，与导出点集一致。
- 回归：新增"界面默认列与导出点集完全一致（界面多出 0、导出多出 0）"等 4 条断言；
  并把 UI 测试里写死的列数期望改为调用产品自己的判定函数 —— 它曾经自己重写了一份
  分组白名单，产品一改就假失败。

### 新增诊断入口 `--diag-page`

```
ExperimentMonitorDemo.exe --diag-page --tab=3 --capture-first --root=<目录>
```

进程内切到指定页签、等它加载，把表格维度/表头/主要标签/按钮写成 `diag-page.json`。
数据记录页的 DataGridView 会让 UI Automation 枚举超过 30 秒上限，
这条路径只能靠进程内驱动 —— 结论一样硬，还不受 UIA 性能干扰。

**注意**：诊断必须复现真实入口的装配（挂 `HistoryPage` / `CloudPage`），
否则量到的表格是别的页面的。第一版就踩了这个坑（量到 37 行×10 列的"测点详情"表）。
